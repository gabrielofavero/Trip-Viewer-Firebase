# Encryption-at-Rest: Firestore & Offline JSON

> **Status:** Draft proposal  
> **Date:** 2026-07-26  
> **Applies to:** Trip Viewer — Firestore protected data + offline JSON exports

---

## 1. Problem Statement

### Current state

Today, Trip Viewer has a **two-tier data model** for sensitive fields:

| Tier | Storage | Access control |
|---|---|---|
| Public fields | `trips/{tripId}`, `accommodations/{id}`, `transportation/{id}`, `expenses/{tripId}` | Firestore security rules (auth UID check) |
| Sensitive fields | `trips/protected/{pin}/{tripId}`, `expenses/protected/{pin}/{tripId}` | Firestore security rules check PIN in path |

Sensitive fields include:
- **Accommodation:** `reservation` codes, `link` URLs
- **Transportation:** `reservation` codes, `link` URLs
- **Expenses:** entire expenses document (when `pin` preference is `"all-data"` or `"sensitive-only"`)

A lightweight lookup document at `protected/{tripId}` stores `{ pin: "1234" }` so the app can locate the protected subcollection path.

### The security gap

1. **Firestore admins / compromised console access** can read plaintext sensitive data directly.
2. **Exported JSON files** (generated by `export-documents.ts`) contain **plaintext** reservation codes and links.
3. **Offline mode** (Epic E043) will distribute JSON files that include plaintext sensitive fields — a stolen `.zip` or `.json` file exposes all trip details.
4. **4-digit PINs** are the only barrier, and they are stored **in plaintext** in `protected/{tripId}` documents, making brute-force trivial for anyone with console/database access.

### What we want

- Sensitive data is **encrypted at rest** in Firestore — even an admin with direct DB access only sees ciphertext.
- Exported JSON files contain the **same encrypted blobs** — the offline app uses identical decryption logic.
- The PIN never appears in plaintext in the database; it is only held in the user's head (or browser session).

## 2. Proposed Architecture

### 2.1 Encryption algorithm

| Parameter | Choice | Rationale |
|---|---|---|
| Key derivation | PBKDF2, SHA-256, 200k iterations | Browser-viable; tunable if performance allows |
| Cipher | AES-256-GCM | Authenticated encryption — detects tampering + wrong PIN |
| Salt | 16 random bytes per PIN group, base64-encoded | Reuse across documents sharing the same PIN for efficiency |
| IV | 12 random bytes per encryption, base64-encoded | Must be unique per operation (GCM requirement) |
| Plaintext | `JSON.stringify(sensitiveObject)` | Deterministic serialization of the sensitive fields |

### 2.2 New Firestore document structure

Protected documents move from the path-based model to an **encrypted payload model**:

```jsonc
// trips/protected/{tripId}  (no longer path-pinned)
{
  "encryptedPayload": {
    "salt": "xK7mP2qR9vL4wN8t...",       // base64, 16 bytes
    "iv": "aB3dE5fG7hI9jK1l...",         // base64, 12 bytes
    "ciphertext": "U29tZSBkYXRhIHRvIGVuY3J5cHQ="  // base64, AES-256-GCM output
  }
}
```

> **Note:** The PIN is no longer stored in `protected/{tripId}`. The new `protected/{tripId}` document only contains the encrypted payload. The PIN is validated by successfully decrypting the payload — wrong PIN → `crypto.subtle.decrypt` throws → catch and return null.

### 2.3 Offline JSON structure (unchanged)

The export format stays the same — but the `protected` section now carries `encryptedPayload` instead of plaintext:

```jsonc
{
  "_meta": { "type": "trip", "exportedAt": "...", "version": "2.0", "sourceId": "abc123" },
  "trip": { /* all public fields */ },
  "accommodations": { /* ... */ },
  "transportation": { /* ... */ },
  "itinerary": { /* ... */ },
  "expenses": { /* public expenses fields if any */ },
  "destinations": { /* ... */ },
  "protected": {
    "encryptedPayload": {
      "salt": "xK7mP2qR9vL4wN8t...",
      "iv": "aB3dE5fG7hI9jK1l...",
      "ciphertext": "U29tZSBkYXRhIHRvIGVuY3J5cHQ="
    }
  }
}
```

The offline app uses the same `decryptPayload(encryptedPayload, pin)` function as the online app. No special offline code path needed.

## 3. Crypto Utility Module (`cryptoUtils.ts`)

A new shared module to be placed at `public/assets/ts/utils/crypto.ts`:

```ts
// ============================================================
// cryptoUtils.ts — AES-256-GCM encryption/decryption for
// Trip Viewer protected data (Firestore + offline JSON).
//
// Uses Web Crypto API (available in browsers and Node.js 19+).
// ============================================================

const ALGORITHM = 'PBKDF2';
const HASH = 'SHA-256';
const ITERATIONS = 200_000;          // Tune for perf on target devices
const KEY_LENGTH = 256;              // AES-256
const ENCRYPTION_ALGO = 'AES-GCM';

// ---- Base64 ↔ ArrayBuffer helpers ----

export function bufferToBase64(buffer: ArrayBuffer): string {
    const bytes = new Uint8Array(buffer);
    let binary = '';
    for (let i = 0; i < bytes.byteLength; i++) {
        binary += String.fromCharCode(bytes[i]);
    }
    return btoa(binary);
}

export function base64ToBuffer(base64: string): ArrayBuffer {
    const binary = atob(base64);
    const bytes = new Uint8Array(binary.length);
    for (let i = 0; i < binary.length; i++) {
        bytes[i] = binary.charCodeAt(i);
    }
    return bytes.buffer;
}

// ---- Key derivation ----

async function deriveKey(pin: string, salt: ArrayBuffer): Promise<CryptoKey> {
    const enc = new TextEncoder();
    const keyMaterial = await crypto.subtle.importKey(
        'raw',
        enc.encode(pin),
        ALGORITHM,
        false,
        ['deriveKey']
    );
    return crypto.subtle.deriveKey(
        {
            name: ALGORITHM,
            salt,
            iterations: ITERATIONS,
            hash: HASH,
        },
        keyMaterial,
        { name: ENCRYPTION_ALGO, length: KEY_LENGTH },
        false,
        ['encrypt', 'decrypt']
    );
}

// ---- Public API ----

export interface EncryptedPayload {
    salt: string;       // base64
    iv: string;         // base64
    ciphertext: string; // base64
}

/**
 * Encrypt a plain JavaScript object with a PIN.
 * @param plainObject  The object to encrypt (will be JSON.stringify'd).
 * @param pin          User-provided PIN/passphrase.
 * @param groupSalt    Optional pre-existing salt (base64). If omitted, a new one is generated.
 *                     Reuse the same salt for all docs sharing a PIN so the derived key is identical.
 * @returns            { salt, iv, ciphertext } all as base64 strings.
 */
export async function encryptData(
    plainObject: Record<string, unknown>,
    pin: string,
    groupSalt?: string
): Promise<EncryptedPayload> {
    const saltBytes = groupSalt
        ? new Uint8Array(base64ToBuffer(groupSalt))
        : crypto.getRandomValues(new Uint8Array(16));
    const iv = crypto.getRandomValues(new Uint8Array(12));

    const key = await deriveKey(pin, saltBytes);
    const plaintext = new TextEncoder().encode(JSON.stringify(plainObject));
    const ciphertext = await crypto.subtle.encrypt(
        { name: ENCRYPTION_ALGO, iv },
        key,
        plaintext
    );

    return {
        salt: bufferToBase64(saltBytes),
        iv: bufferToBase64(iv),
        ciphertext: bufferToBase64(ciphertext),
    };
}

/**
 * Decrypt an EncryptedPayload back to a plain object.
 * @param encryptedObj  { salt, iv, ciphertext } (all base64).
 * @param pin           User-provided PIN/passphrase.
 * @returns             The original plain object, or null if decryption fails (wrong PIN).
 */
export async function decryptData(
    encryptedObj: EncryptedPayload,
    pin: string
): Promise<Record<string, unknown> | null> {
    try {
        const salt = base64ToBuffer(encryptedObj.salt);
        const iv = base64ToBuffer(encryptedObj.iv);
        const ciphertext = base64ToBuffer(encryptedObj.ciphertext);

        const key = await deriveKey(pin, salt);
        const decrypted = await crypto.subtle.decrypt(
            { name: ENCRYPTION_ALGO, iv },
            key,
            ciphertext
        );
        return JSON.parse(new TextDecoder().decode(decrypted));
    } catch {
        // Wrong PIN or corrupted data — crypto.subtle.decrypt throws
        return null;
    }
}
```

## 4. Migration Strategy

### 4.1 What gets encrypted

The sensitive fields currently stored in `trips/protected/{pin}/{tripId}`:

```ts
interface ProtectedTripData {
    hospedagens: Record<string, { reservation: string; link: string }>;  // accId → sensitive
    transporte: Record<string, { reservation: string; link: string }>;   // legId → sensitive
}
```

And for expenses with `pin: "all-data"`: the entire expenses document fields (`preTrip`, `duringTrip`).

### 4.2 Migration phases

#### Phase A — Crypto module (no data change)
- Add `cryptoUtils.ts` to the codebase.
- Write unit tests (encrypt → decrypt roundtrip, wrong PIN → null, tampered ciphertext → null).
- Integrate into the build pipeline.

#### Phase B — Migration script (Firestore transform)
- A Node.js script (`scripts/migrate/encrypt-protected-data.ts`) that:
  1. Reads all `protected/{tripId}` documents to get `{ pin }`.
  2. For each trip, reads `trips/protected/{pin}/{tripId}` (plaintext sensitive data).
  3. Generates a **group salt** per PIN (reused across all docs with the same PIN).
  4. Encrypts the sensitive data using `encryptData()`.
  5. Writes the encrypted payload to `protected/{tripId}` (overwriting the `{ pin }` doc).
  6. Deletes the old `trips/protected/{pin}/{tripId}` documents.
  7. Does the same for expenses: `expenses/protected/{pin}/{tripId}` → encrypted payload in `expensesProtected/{tripId}`.

- **Run in a secure local environment** (developer machine, with emulator first, then production).

#### Phase C — App read path update
- Update `fetchProtectedData()` in `export-documents.ts` and all in-app readers:
  - Old: `getDocument('trips/protected/' + pin + '/' + tripId)` → returns plaintext.
  - New: `getDocument('protected/' + tripId)` → returns `{ encryptedPayload }` → `await decryptData(encryptedPayload, pin)`.
- Update the PIN entry flow: remove the "fetch PIN from `protected/{id}`" step; PIN validation now happens via decryption attempt.

#### Phase D — Export update
- `buildTripExport()` already reads protected data via `fetchProtectedData()`. After Phase C, the export JSON naturally contains the encrypted payload instead of plaintext — **no change needed** to the export structure.
- Bump `_meta.version` to `"2.0"` for encrypted exports.

#### Phase E — Offline decryption
- The offline HTML/JS app (Epic E043) includes `cryptoUtils.ts` and calls `decryptData()` with the user's PIN when displaying sensitive fields.
- No special offline-only decryption code — identical to the online path.

### 4.3 Rollback plan

- Keep the old `trips/protected/{pin}/{tripId}` documents for a grace period (e.g., 30 days) before deletion.
- The migration script can be run in reverse: decrypt payloads → write back plaintext → restore old structure.

## 5. Security Considerations

| Concern | Mitigation |
|---|---|
| **4-digit PIN brute-force** | 4 digits = 10k possibilities. PBKDF2 with 200k iterations makes each attempt ~100ms. Offline brute-force of a single JSON would take ~17 minutes. This is not great — encourage **6+ digit PINs or passphrases** in the UI. |
| **Salt reuse across PIN group** | Intentional — same PIN → same derived key. IV is always unique per encryption, so ciphertexts differ. No security degradation (standard practice for key-wrapping scenarios). |
| **Side-channel via document size** | Encrypted payloads have similar sizes regardless of content. The `salt` + `iv` + `ciphertext` structure reveals nothing about the plaintext. |
| **Migration script security** | Must run on a trusted machine. The script temporarily holds plaintext in memory — use `crypto.getRandomValues` for salt/IV (not `Math.random()`). |
| **PIN still in browser memory** | Unavoidable — the user types the PIN into the browser. Mitigate with: clear PIN from JS variables after use, add UI rate-limiting (client-side delay after 3 failed attempts). |
| **Offline JSON distribution** | Add a warning in the exported file and UI: *"This file contains encrypted sensitive data. Protect it like you would protect your PIN."* |
| **Firestore security rules** | Update rules: `protected/{tripId}` is readable by the document owner only (no PIN in path means simpler rules). The encrypted payload is safe even if rules are misconfigured. |

### Relationship to Epic E043 (Offline Mode)

This encryption work should be completed **before** E043's export pipeline goes into production. The offline JSON files must contain encrypted blobs, not plaintext. Fortunately, the export format already supports this — the `protected` key in the export JSON simply changes from carrying plaintext to carrying `encryptedPayload`.

### Backward compatibility

- Old plaintext `trips/protected/{pin}/{tripId}` documents should be migrated (Phase B) before the app code changes (Phase C).
- During transition, the app can try the new encrypted path first, fall back to the old plaintext path — log a warning for unmigrated documents.

## 7. Open Questions

1. **PIN length requirement:** Should we enforce a minimum of 6 digits? 4-digit PINs are crackable in ~17 minutes offline. A 6-digit PIN with 200k iterations takes ~28 hours.
2. **Passphrase support:** Allow alphanumeric PINs? PBKDF2 works with any string — the UI currently uses 4 numeric input boxes. This would require a UI change.
3. **Per-document salt vs. group salt:** The current proposal uses group salt (same salt for all docs with the same PIN). Pro: single key derivation, faster bulk operations. Con: if one doc's salt is exposed, the attacker can derive the key for all docs in that PIN group. Since the salt is stored right next to the ciphertext anyway, this is a minor concern — the salt is not secret.
4. **Migration window:** How long do we keep the old plaintext docs before deletion? Suggestion: 30 days.
5. **Expenses with `pin: "sensitive-only"`:** The expenses document at `expenses/{tripId}` is currently public. With `sensitive-only`, does any expenses data get encrypted? Based on current code, only the `expenses/protected/{pin}/{tripId}` variant is affected — the public `expenses/{tripId}` remains plaintext for `sensitive-only` trips.
